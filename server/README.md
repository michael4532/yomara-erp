ERP modulaire de Yomara Technologies. Une seule base de code pour deux usages :

- **Installation unique** (`ERP_MODE=single`) : le client installe sa copie sur son hébergement.
- **Plateforme SaaS** (`ERP_MODE=saas`) : une installation, plusieurs sociétés abonnées (inscription, formules, essai).

L'interface est l'application Flutter (Windows, macOS, Linux, Web). La version Web est déjà compilée dans `public/app`.

## Installation sur hébergement mutualisé (cPanel, Plesk…)

1. Créez une base MySQL/MariaDB et son utilisateur depuis le panneau.
2. Envoyez le contenu du zip dans le dossier du domaine (ou d'un sous-domaine, ex. `erp.mondomaine.ci`).
   - Idéal : faire pointer la racine du domaine vers le dossier `public/`.
   - Sinon : le fichier `.htaccess` racine redirige automatiquement vers `public/` et bloque l'accès aux fichiers sensibles.
3. Ouvrez `https://votre-domaine/install` et suivez l'assistant : prérequis → base de données → société et administrateur.
4. Ajoutez la tâche cron indiquée en fin d'installation (toutes les minutes) :
   `* * * * * php /chemin/artisan schedule:run >> /dev/null 2>&1`

Prérequis : PHP 8.2+, extensions pdo_mysql, mbstring, openssl, tokenizer, xml, ctype, json, fileinfo, curl (et zip + xmlreader pour lire et écrire les fichiers Excel ; sans elles, l'import / export fonctionne en CSV ; gd pour les signatures électroniques et les images ; `qpdf` facultatif sur VPS pour reprendre les pages des PDF récents dans les documents signés). Aucun Node, Redis ni Composer nécessaire sur le serveur (le dossier `vendor` est fourni).

## Architecture des modules

Chaque module vit dans `app/Modules/<Nom>/` :

```
app/Modules/Stock/
├── module.php        # manifeste : clé, nom, dépendances, permissions, entités synchronisées, tableau de bord
├── routes.php        # routes API, préfixées /api/<clé> et protégées par le middleware module:<clé>
├── migrations/       # tables du module
├── Models/           # modèles (trait Syncable pour le hors ligne)
├── Dashboard.php     # indicateurs affichés au tableau de bord
└── StockModuleProvider.php  # écouteurs d'événements (facultatif)
```

Ajouter un module :

1. Créez le dossier et `module.php` (voir `app/Modules/Stock/module.php`).
2. Modèles : `use Syncable;` + `$syncEntity`, `$viewPermission`, `$managePermission`, `syncRules()`.
3. Routes CRUD en une ligne : `EntityController::routes('vehicules', Vehicule::class);`
4. Déclarez la clé dans `config/erp_catalog.php` (catégorie, prix de départ).
5. `php artisan migrate && php artisan erp:modules-sync` → le module apparaît dans le super admin, activable et tarifable, et ses données se synchronisent hors ligne sans code supplémentaire.

Si le super admin coupe un module, ses routes répondent `403 module_disabled` et ses entités sortent de la synchronisation.

## Synchronisation hors ligne (protocole)

- `GET /api/sync/pull?cursor=N` → `{cursor, has_more, changes: {entité: {upserts: [...], deletes: [ids]}}}`
- `POST /api/sync/push` → `{mutations: [{id, entity, op: upsert|delete, record_id, data, base_version}]}`
  - Chaque mutation porte un UUID : un renvoi après coupure n'est jamais appliqué deux fois.
  - `base_version` ≠ version serveur → `conflict`, la version serveur est renvoyée.
  - Les documents sont numérotés **par le serveur** à la validation (pas de doublon entre appareils hors ligne).
  - Le stock est un journal de mouvements : deux caisses hors ligne peuvent vendre en même temps sans conflit.

## Caisse hors ligne : comment ça marche

- Chaque ticket reçoit un **numéro provisoire propre à la caisse** (`C1-000123`) imprimé immédiatement ; le serveur attribue le numéro légal (`TK-2026-00045`) à la synchronisation et garde le provisoire en référence.
- Ouverture et clôture de session se font hors ligne. À la synchro, le serveur **recalcule** ventes, espèces attendues et écart à partir des tickets réellement reçus ; un ticket arrivé en retard d'un autre appareil met à jour une session déjà clôturée.
- Le stock baisse immédiatement sur l'appareil, puis le serveur génère les mouvements définitifs.
- **Arrondis franc CFA** : pour les devises sans centimes (XOF, XAF, GNF…), les totaux partent du prix TTC arrondi au franc, ce qui respecte les prix de rayon (4 × 500 F = 2 000 F). Les autres devises gardent le calcul HT → TVA au centime.

| Ancienneté | 2 % à 2 ans, + 1 % par an, maximum 25 % |
| Prorata | salaire × jours payés / 30 |

Exemple de contrôle (test automatisé) : marié, 2 enfants, brut 500 000 F → ITS 81 000 − 22 000 = 59 000 F, CNPS 31 500 F, CMU 1 500 F, net 408 000 F.

**À faire valider par un expert-comptable ou un spécialiste paie avant la première paie réelle.**

## Présence (personnes connectées)

Chaque requête de l'app met à jour `last_seen_at`, la plateforme (`X-Client-Platform` : windows, macos, linux, web…) et l'IP (au plus toutes les 30 s). L'app envoie un signal toutes les 60 s. Est « en ligne » quiconque a été actif depuis `ERP_PRESENCE_WINDOW` secondes (120 par défaut).

## Points à compléter avant commercialisation

- Encaissements Mobile Money par SMS : les formats de SMS changent parfois chez les opérateurs ; vérifier avec de vrais SMS de vos comptes marchands (le SMS non reconnu reste « à traiter », rien n'est perdu).

- Serveur de licences (la clé est enregistrée mais pas encore vérifiée à distance).
- Lecture des factures fournisseurs : les PDF « texte » sont lus partout (pdftotext si disponible, sinon PHP) ; les photos et PDF scannés demandent `tesseract` (paquets `tesseract-ocr` et `tesseract-ocr-fra`, VPS) et `exec` autorisé — rarement le cas en mutualisé. Extraction heuristique : à valider sur des factures réelles de fournisseurs ivoiriens.
- Essais réels de chaque prestataire de paiement, SMS et WhatsApp avec des clés de test.
- Modules du catalogue marqués « Bientôt ».
